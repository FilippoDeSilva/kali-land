# Kali-land — Architecture Refinement & BYOS Hardening

You are working on **Kali-land**, an open-source desktop foundation for Kali Linux.

Repository:
`https://github.com/FilippoDeSilva/kali-land`

## Mission

Refine the existing project so that its implementation fully matches its architectural philosophy.

The goal is **NOT** to turn Kali-land into another Omarchy, another rice, or a giant opinionated desktop distribution.

The goal is to make Kali-land a **minimal, robust, composable desktop foundation** that can safely coexist with whatever configuration, shell, workflow, applications, dotfiles, and personal choices the user already has.

The core philosophy is:

> **Kali-land owns the plumbing, not the personality.**

and:

> **Kali-land provides the floor, not the furniture.**

The user should be able to install Kali-land and then bring essentially any compatible desktop setup on top of it without Kali-land destroying, silently replacing, or taking ownership of unrelated user configuration.

# 2. THE CORE ARCHITECTURAL RULE

Kali-land must distinguish between:

### Kali-land-owned resources

Things Kali-land explicitly creates, installs, modifies, or manages.

Examples:

* packages installed by Kali-land
* binaries installed by Kali-land
* files generated by Kali-land
* directories created exclusively for a Kali-land integration
* platform configuration explicitly owned by Kali-land
* state under:
  `~/.local/state/kali-land/`

### User-owned resources

Everything else.

Examples:

* existing dotfiles
* existing Hyprland configuration
* existing Quickshell configurations
* existing Waybar configuration
* existing terminal configuration
* Neovim configuration
* tmux configuration
* systemd user services
* custom scripts
* environment configuration
* wallpapers
* themes
* keybindings
* animations
* custom shell layouts
* personal application configuration
* arbitrary dotfiles repositories

The core must **not assume it understands user-owned resources.**

This is extremely important:

> **Generic does not mean understanding every possible user setup.**
>
> Generic means Kali-land does not need to understand it.

If a user brings something Kali-land does not recognize, the default behavior should be:

**leave it alone.**

# 3. DO NOT OVERENGINEER THE CORE

Do NOT introduce:

* a giant plugin framework
* unnecessary abstraction layers
* a universal configuration DSL
* a massive schema system
* an enormous dependency injection architecture
* a complicated daemon
* a database
* a giant package-management replacement

Keep the implementation primarily shell-based and understandable.

Introduce abstractions only where they solve an actual architectural problem.

The most important abstraction we need is:

# RESOURCE OWNERSHIP / PROVENANCE

---

# 4. IMPLEMENT A RESOURCE OWNERSHIP LEDGER

Create a persistent state/ownership mechanism under:

```text
~/.local/state/kali-land/
```

Suggested structure:

```text
~/.local/state/kali-land/
├── state/
│   └── installation.json
├── backups/
├── logs/
└── reports/
```

The exact format may differ if you have a better lightweight design, but it must be:

* deterministic
* human-readable
* robust
* easy to inspect
* safe to update
* usable by installer/uninstaller/doctor/rollback
* versionable
* attributable

The ledger should track at least:

### Installation metadata

```text
installation ID
Kali-land version
timestamp
profile
platform
```

### Packages

For each package:

```text
package name
requested by Kali-land
already existed before installation?
installed by Kali-land?
```

Potential states:

```text
already_present
installed_by_kali_land
failed
```

Do NOT assume:

> "package appears in packages/*.txt => Kali-land owns it"

That is incorrect.

---

# 5. FILE / DIRECTORY OWNERSHIP

Track resources at an appropriate granularity.

For example:

```text
~/.config/quickshell/end4-pC/
```

can be Kali-land-owned by an integration.

But:

```text
~/.config/quickshell/
```

should NOT automatically become Kali-land-owned.

Likewise:

```text
~/.config/hypr/kali-land/
```

can be safely owned by Kali-land.

But blindly claiming:

```text
~/.config/hypr/
```

as Kali-land-owned is dangerous if the user already has their own Hyprland configuration.

The ownership model must distinguish:

```text
created
modified
backed_up
owned
user_owned
```

where appropriate.

---

# 6. FIX QUICKSHELL OWNERSHIP

This is one of the highest-priority fixes.

The current implementation targets the parent:

```text
~/.config/quickshell
```

This is NOT acceptable for true BYOS.

Never replace or delete the entire parent directory simply because Kali-land is installing one integration.

Instead use an integration-specific namespace such as:

```text
~/.config/quickshell/end4-pC/
```

or another appropriate isolated path.

If the user already has:

```text
~/.config/quickshell/
├── celestia/
├── my-shell/
├── experiments/
└── custom/
```

installing `end4-pC` must NOT touch those directories.

The same principle must apply to future integrations.

---

# 7. MAKE INTEGRATIONS ACTUALLY MODULAR

The integration architecture should become genuinely generic.

An integration should declare things such as:

```yaml
name: example-shell
type: quickshell

requires:
  - wayland
  - hyprland
  - quickshell

optional:
  - pipewire
  - networkmanager
  - bluetooth

launch:
  command: ...
```

But do not hardcode:

```text
quickshell
```

as a universal requirement of Kali-land itself.

The integration should declare its runtime.

For example:

```text
runtime: quickshell
```

Then another integration could theoretically use:

```text
runtime: something-else
```

without modifying the core architecture.

Do NOT implement fake universal support for every possible runtime.

Implement the abstraction cleanly and allow real integrations to define what they need.

---

# 8. QUICKSHELL MUST BECOME OPTIONAL

The minimal Kali-land installation should not inherently mean:

```text
install Quickshell
install end4-pC
install Matugen
```

unless the selected installation/profile explicitly requests them.

The core platform should be usable without a shell integration.

Think in terms of:

```text
Kali-land core
    ├── Wayland foundation
    ├── Hyprland foundation
    ├── desktop services
    └── lifecycle infrastructure

Optional integrations
    ├── end4-pC
    ├── future Quickshell shell
    ├── future alternative shell
    └── user-provided integration
```

The user should be able to choose:

### Minimal

```text
Kali-land platform only
```

### Platform + integration

```text
Kali-land
+ end4-pC
```

### Platform + another integration

```text
Kali-land
+ another supported shell
```

### Platform + completely user-managed experience

```text
Kali-land
+ user's own shell/configuration
```

The last case must be a first-class valid state.

---

# 9. HYPRLAND OWNERSHIP MUST BE RECONSIDERED

Hyprland is part of the platform, but the user's Hyprland configuration is potentially user-owned.

Do not casually overwrite:

```text
~/.config/hypr/
```

if it contains user configuration.

Determine exactly what Kali-land actually needs from Hyprland.

Prefer an architecture where Kali-land-owned configuration is isolated.

For example:

```text
~/.config/hypr/
├── kali-land/
│   ├── platform.conf
│   ├── environment.conf
│   └── ...
├── user.conf
└── user's existing configuration
```

or an equivalent clean mechanism.

The exact structure is up to you after inspecting the current code.

The important rule is:

> Kali-land must not silently become the owner of the user's entire Hyprland configuration.

Audit things like:

* terminal selection
* Quickshell environment variables

* shell startup
* shell-specific `sed` modifications
* Matugen assumptions
* VMware-specific terminal substitutions

```text

    assume end4-pC
    assume Quickshell
    assume Kitty
    assume Matugen
```

Instead:

```text

```

# 11. VMWARE SUPPORT MUST NOT BREAK BYOS

Audit VMware detection carefully.

Current behavior modifies configuration depending on whether the machine is virtualized.

This must not result in Kali-land silently rewriting unrelated user configuration.

If VMware requires:

```text
foot
```

instead of:

```text
kitty
```

determine whether that is actually a platform requirement or merely a current integration implementation detail.

Do not preserve accidental historical assumptions.

Platform detection should expose facts/capabilities.

Profiles or integrations should decide how to use them.

---

# 12. BACKUPS MUST BECOME OWNERSHIP-AWARE

The current backup system is a good foundation.

Preserve its useful properties:

* timestamped backups
* manifests
* restore capability
* state directory
* rollback

But improve the semantics.

A backup should answer:

```text
What did Kali-land protect?
Why did it protect it?
What component changed it?
What installation changed it?
Where was the original?
Can it be restored?
```

Do not treat:

```text
backup exists
```

as equivalent to:

```text
Kali-land owns this entire resource.
```

That distinction is critical.

---

# 13. NEVER USE BACKUP AS AN EXCUSE TO OVERWRITE USER DATA

This is a fundamental requirement.

Bad:

```text
backup ~/.config/quickshell
rm -rf ~/.config/quickshell
install end4-pC
```

Even though there is a backup.

Why?

Because the user's configuration was still destroyed from their live system.

Correct:

```text
inspect target
determine exact resource Kali-land needs
backup exact resource if necessary
modify only that resource
record ownership
leave everything else untouched
```

Backups are a safety net, not permission to overwrite.

---

# 14. UNINSTALL MUST BECOME OWNERSHIP-AWARE

Current uninstall logic contains static lists such as:

```text
hypr
quickshell
kitty
foot
mako
wlogout
hyprlock
hypridle
```

This is dangerous for a truly generic system.

Example:

A user had Kitty before installing Kali-land.

Kali-land must NOT uninstall Kitty merely because:

```text
kitty
```

appears in Kali-land's package list.

Similarly, if the user had an existing:

```text
~/.config/kitty/
```

Kali-land must not delete it merely because Kitty is a Kali-land-supported application.

The uninstall process must answer:

> Did Kali-land create/modify/own this resource?

If no:

**leave it alone.**

---

# 15. PACKAGE OWNERSHIP

Track package provenance.

Example:

Before installation:

```text
hyprland -> installed
pipewire -> installed
kitty -> absent
```

Kali-land installs:

```text
kitty
```

The ledger should record:

```text
hyprland: already_present
pipewire: already_present
kitty: installed_by_kali_land
```

Later:

```bash
kali-land uninstall --remove-packages
```

should NOT blindly remove all packages from the package lists.

It should primarily remove packages Kali-land actually installed, subject to safe dependency handling.

Be careful with packages that became dependencies of other software.

Do not implement unsafe:

```bash
apt remove everything we ever listed
```

logic.

---

# 16. DEFAULT UNINSTALL SHOULD REMAIN CONSERVATIVE

Preserve the current philosophy that normal uninstall should be safe.

Default uninstall should ideally mean:

```text
remove Kali-land-owned runtime/platform artifacts
preserve user configurations
preserve unrelated packages
preserve backups/state where useful
```

More destructive operations should require explicit flags.

For example:

```text
--remove-configs
--remove-packages
--remove-backups
```

But even those flags must respect ownership.

A flag saying:

```text
--remove-configs
```

must NOT mean:

> Delete every configuration with a name that Kali-land happens to know about.

It means:

> Remove configurations/resources that the ownership ledger says Kali-land owns.

---

# 17. ROLLBACK MUST USE THE SAME OWNERSHIP MODEL

Rollback should not have its own separate understanding of the system.

The lifecycle should conceptually be:

```text
install
   ↓
record ownership
   ↓
backup modified resources
   ↓
apply changes
   ↓
record resulting state
```

Then:

```text
rollback
   ↓
read ownership/state
   ↓
restore only affected resources
   ↓
preserve unrelated user resources
```

The same provenance information should support:

* install
* update
* backup
* rollback
* uninstall
* doctor

Avoid five independent ownership systems.

---

# 18. UPDATE MUST ALSO BE SAFE

Think beyond fresh installation.

Suppose:

```text
Kali-land v1
```

creates:

```text
~/.config/hypr/kali-land/platform.conf
```

The user later modifies:

```text
~/.config/hypr/user.conf
```

Then Kali-land updates to v2.

The update must not overwrite:

```text
user.conf
```

because it happens to live in the same parent directory.

Kali-land should update only resources it owns.

If a resource has become user-modified, detect that where practical and avoid blindly overwriting it.

Do not build a sophisticated three-way merge system unless actually necessary.

A safe warning/skip strategy is better than destructive automation.

# 35. DEFINITION OF DONE

Do not consider the work complete merely because:

```bash
install
```

works.

The project is complete when the following architectural statement is true:

> A user can install Kali-land on a system containing an existing desktop configuration, and Kali-land can provide its platform capabilities without needing to understand or take ownership of the user's personal desktop experience.

And:

> Installing one integration does not implicitly own the parent configuration directory.

And:

> Uninstalling Kali-land removes Kali-land-owned resources rather than resources merely known to Kali-land.

And:

> Packages are removed based on provenance rather than package-list membership alone.

And:

> Backup, rollback, update, doctor, and uninstall all understand the same ownership model.

And:

> A system with no optional shell integration is still a valid Kali-land installation.

And:

> `end4-pC` is an integration, not the core.

And:

> The core remains minimal and unopinionated.

```bash

```

1. Who owns this directory?
2. Did Kali-land create it?
3. Did Kali-land modify it?

6. Can the operation be narrowed to an exact resource?
7. Is the operation recorded in the ownership ledger?
8. Can it be restored?

If the answer is unclear:

**do not perform the destructive operation.**

Prefer isolation.

# 40. FINAL INSTRUCTION

Do not optimize for:

> "How can Kali-land configure everything?"

Optimize for:

> **"How can Kali-land provide a strong foundation while touching as little user-owned configuration as possible?"**

That is the product.

The goal is not maximum automation.

The goal is:

**maximum capability + minimum ownership.**

Keep the core stupidly minimal.

Keep the architecture composable.

Keep integrations isolated.

Keep lifecycle operations reversible.

Keep user configuration sacred.

And make the implementation finally match the project's philosophy:

> **Kali-land owns the environment; the user owns the experience.**
